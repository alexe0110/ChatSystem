# ADR-004: In-memory Hub вместо распределённого pub/sub

## Status

Accepted

## Context

Bidirectional gRPC-стрим `Chat` требует маршрутизации сообщений между
подключёнными пользователями в реальном времени. Нужен механизм pub/sub.

Варианты:
- **In-memory Hub** — `map[UUID]chan` под mutex, всё внутри одного процесса
- **Redis Pub/Sub** — распределённый, работает между инстансами
- **Kafka** — полноценный message broker

## Decision

In-memory Hub (`internal/hub/hub.go`): `map[uuid.UUID]chan *pb.ChatMessage`
с `sync.RWMutex`. Register создаёт буферизованный канал (cap=10),
Send пишет в канал получателя, Unregister закрывает канал.

Это осознанное решение, в ECS — при одном инстансе распределённый pub/sub не нужен.

При масштабировании проекта следует перейти на нормальный брокер сообщений

## Consequences

**Плюсы:**
- Нулевая внешняя зависимость — нет Redis/Kafka в инфраструктуре
- Минимальная латентность — запись в канал = наносекунды
- Простой код, легко понять и отладить
- Достаточно для MVP и демонстрации паттерна

**Минусы:**
- Работает только в рамках одного процесса. Пользователи
  на разных инстансах не видят сообщения друг друга
- `Send` блокирует если буфер канала полный (cap=10) — медленный получатель
  может застопорить отправителя. Нужен `select` с `default` (drop) или таймаутом
- Нет персистентности — при рестарте контейнера все подключения теряются

**Путь миграции:**
При переходе к нескольким инстансам — заменить Hub на Redis Pub/Sub:
подписка на `chat:{user_id}`, publish при Send. Интерфейс Hub не меняется,
меняется реализация.
